# Очерёдность выделения сервисов

## Контекст
Текущий монолит не справляется с пиковыми нагрузками. Требуется строгая последовательная декомпозиция монолита по одному сервису за этап, с минимизацией downtime и поэтапным наращиванием event-driven каналов.

## Решение

### План миграции
| Шаг   | Выделяемый сервис | Цель этапа                                              | Ключевой артефакт перехода                |
|-------|-------------------|---------------------------------------------------------|-------------------------------------------|
| **1** | `Notification`    | Снять нагрузку с монолита, внедрить async-каналы        | Outbox → Kafka → Consumer                 |
| **2** | `Geography`       | Изолировать внешние интеграции (карты, геокодинг)       | API Gateway proxy + caching               |
| **3** | `Driver`          | Развязать статусы и геопозиции, запустить event-поток   | `DriverLocationUpdated` topic             |
| **4** | `Booking`         | Выделить ядро транзакций, внедрить асинхронный матчинг  | Saga starter, dual-write cut-over         |
| **5** | `Pricing`         | Включить real-time расчёт на стабилизированных событиях | Redis cache + Kafka Streams enrichment    |
| **6** | `Payments`        | Гарантировать финансовую консистентность                | Transactional Outbox, compensating events |
| **7** | `Fraud`           | Подключить скоринг к зрелому event-потоку               | Real-time scoring consumer + DLQ          |
| **8** | `Analytics`       | Завершить пайплайн, включить BI/ML агрегацию            | ClickHouse ELT, materialized views        |

### Логика выделения сервисов
1. **Notification → 1**: Асинхронный, stateless-ориентированный, не влияет на транзакционную консистентность. Быстрая отдача, снижение нагрузки на монолит.
2. **Geography → 2**: Внешние API и read-heavy запросы. Легко проксируется через Gateway, не требует сложных миграций БД.
3. **Driver → 3**: Критичен для матчинга. Выделение первым из «тяжёлых» доменов позволяет запустить базовый event-поток (`LocationUpdated`), необходимый для последующих сервисов.
4. **Booking → 4**: Ядро бизнеса. Мигрируется после абстрагирования зависимостей (Driver, Geography). Позволяет внедрить асинхронный матчинг и снизить latency.
5. **Pricing → 5**: Зависит от событий Booking и Driver. Требует low-latency кэширования. Выделяется на стабильном event-потоке.
6. **Payments → 6**: Финансовые транзакции требуют mature Outbox/Saga. Миграция после стабилизации Booking минимизирует риск рассинхрона.
7. **Fraud → 7**: Аналитический/оценочный сервис. Потребляет события из уже мигрированных доменов, работает без блокировки core-флоу.
8. **Analytics → 8**: Финальный потребитель. Извлекается последним, когда все доменные события структурированы и консистентны.

### Компромиссы
- **Временная двойная запись (Dual-Write)** на каждом шаге увеличивает нагрузку на БД на 10–15% до момента полного cut-over.
- **Заморозка фич** в мигрируемом домене на 2–3 недели этапа для стабилизации контрактов.
- **Eventual Consistency** для некритичных путей (Driver, Notification) на первых шагах, компенсируется idempotent consumers.

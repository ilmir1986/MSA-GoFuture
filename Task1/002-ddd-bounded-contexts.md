# Карта сервисов с доменными границами

## Контекст
Текущий монолит на Django объединяет все бизнес-правила, данные и интеграции в единой кодовой базе и одной БД. Это создаёт сильную связанность, блокирует независимый деплой команд и мешает масштабированию под 500k concurrent trips. Требуется чёткое разделение по бизнес-доменам в соответствии с 8 продуктовыми командами и платформенной функцией.

## Требования
- Чёткие границы ответственности для каждого домена.
- Минимизация cross-domain зависимостей.
- Подготовка к независимому жизненному циклу сервисов (своя БД, свой CI/CD).
- Явное выделение синхронных и асинхронных точек взаимодействия.

## Решение
Выделено 8 бизнес-доменов + 1 платформенный контур. Для каждого зафиксирована зона ответственности, ключевые агрегаты и тип данных.

| Домен | Зона ответственности | Ключевые агрегаты / Сущности | Хранилище |
|-------|---------------------|------------------------------|-----------|
| `Booking` | Управление жизненным циклом поездки, матчинг, статусы | `Trip`, `Booking`, `Route`, `Passenger` | PostgreSQL |
| `Driver` | Профили, статусы доступности, рейтинги, верификация | `Driver`, `Vehicle`, `AvailabilityState`, `Rating` | PostgreSQL |
| `Pricing` | Динамические тарифы, мультипликаторы спроса, калькуляция | `PriceRule`, `FareEstimate`, `SurgeMultiplier` | PostgreSQL + Redis (cache) |
| `Payments` | Транзакции, биллинг, интеграции с шлюзами, выплаты | `Payment`, `Transaction`, `Wallet`, `Payout` | PostgreSQL |
| `Notification` | Мультиканальные оповещения, шаблоны, статусы доставки | `NotificationTemplate`, `ChannelConfig`, `DeliveryLog` | PostgreSQL + FCM/APNS/Huawei |
| `Geography` | Геокодинг, маршрутизация, зоны, трафик, картография | `Location`, `RouteSegment`, `GeoZone`, `TrafficData` | PostgreSQL + Elasticsearch (geo-queries) |
| `Analytics` | Агрегация событий, BI-отчёты, метрики эффективности | `EventStream`, `Report`, `MetricSnapshot` | ClickHouse |
| `Fraud` | Детекция аномалий, скоринг рисков, блокировки | `RiskScore`, `FraudRule`, `Alert`, `Blacklist` | PostgreSQL + Redis (real-time) |
| `Platform` | API Gateway, Service Discovery, Config, CI/CD, Observability | `GatewayRoute`, `FeatureFlag`, `ServiceInstance` | Config DB / etcd |

### Матрица зависимостей
| Источник → Цель | Тип | Обоснование |
|----------------|-----|-------------|
| `Booking` → `Driver` | Async (Kafka) | Матчинг без блокировки; статусы обновляются через события |
| `Booking` → `Pricing` | Sync (REST/gRPC) | Расчёт стоимости перед подтверждением бронирования |
| `Booking` → `Geography` | Sync | Построение маршрута и оценка ETA |
| `Booking` → `Payments` | Async | Запуск транзакции после завершения поездки |
| `Driver` → `Geography` | Async | Периодическая отправка геопозиций |
| `Pricing` → `Analytics` | Async | Обучение моделей на исторических данных |
| `Payments` → `Fraud` | Sync | Pre-check перед проведением платежа |
| All → `Platform` | Sync/Async | Маршрутизация, аутентификация, конфигурация, трейсинг |

## Альтернативы
| Вариант | Плюсы | Минусы | Причина отклонения |
|---------|-------|--------|-------------------|
| Техническая декомпозиция по слоям (UI/Service/DAO) | Проще в начальной реализации | Не даёт бизнес-независимости, сохраняет монолитную связанность | Не соответствует стратегии DDD и автономности команд |
| Shared-библиотека доменной логики | Уменьшает дублирование кода | Блокирует независимый релиз, создаёт version hell | Нарушает принцип автономного деплоя микросервисов |
| Event Sourcing для всех контекстов | Полная история изменений, аудит | Высокая сложность, избыточно для некритичных доменов | Применять выборочно (Booking/Payments), не глобально |

## Компромиссы
- **Дублирование данных**: Профили пользователей/водителей будут дублироваться в `Booking`, `Notification`, `Fraud` для снижения coupling. Синхронизация через Outbox + Kafka.
- **Eventual Consistency**: Отказ от 2PC/XA в пользу компенсационных событий (Saga) для повышения доступности.
- **Миграционная сложность**: Переход от единой PostgreSQL к per-service схемам потребует временного dual-write и CDC.
